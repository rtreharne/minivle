{% if section == 'overview' %}

MiniVLE is an LTI Platform for testing external learning tools. This guide describes its current development interface and the contract a tool must meet.

Vocabulary

Registration
The platform record of a tool’s public configuration and capabilities.
Client ID
The identifier issued by the platform to one registered tool.
Deployment
The activation of that registration in a platform or course context.
Placement
A visible course link that launches the tool.
Launch
A short-lived, signed LTI message sent after OIDC authentication.
JWKS
A public JSON Web Key Set used to verify signatures.

Key ownership

A tool owns its private signing key. Give MiniVLE only the corresponding public JWK or JWKS URL. MiniVLE’s platform private key is separate and is never sent to the tool.

{% elif section == 'getting-started' %}

Use two local applications: MiniVLE at http://localhost:8000 and your tool at http://localhost:9000.

  1. Start MiniVLE with docker compose up --build.
  2. Set LTI_PRIVATE_KEY, LTI_KEY_ID, and LTI_ISSUER=http://localhost:8000.
  3. Run your tool and publish its public JWKS endpoint.
  4. As an instructor, open a course’s LTI tools page, register the tool, then add a placement.
  5. Use a learner account or masquerade mode to exercise the launch.

{% elif section == 'registration' %}

MiniVLE currently supports native manual registration from a course’s LTI tools page. JSON paste/import and Dynamic Registration are planned, not active features.

Current manual fields

  • Name and launch URL
  • LTI version: 1.3
  • Issuer, client ID, deployment ID, and tool JWKS URL

Planned JSON import shape

{ "title": "Local example tool", "description": "A local LTI 1.3 test tool", "oidc_initiation_url": "http://localhost:9000/oidc/login", "target_link_uri": "http://localhost:9000/lti/launch", "redirect_uris": ["http://localhost:9000/lti/launch"], "public_jwk_url": "http://localhost:9000/.well-known/jwks.json", "scopes": ["https://purl.imsglobal.org/spec/lti-nrps/scope/contextmembership.readonly"], "placements": [{"placement": "course_navigation", "text": "Example tool"}] }

The tool supplies URLs and public keys. MiniVLE will issue the client ID and deployment ID when its registration/deployment workflow is complete.

{% elif section == 'launches' %}

LTI 1.3 uses third-party initiated OpenID Connect followed by a signed id_token delivered with form_post.

  1. A user selects a course placement.
  2. MiniVLE reaches the tool’s OIDC initiation endpoint with issuer, client ID, and target-link details.
  3. The tool checks issuer/client ID, then stores short-lived state and nonce.
  4. The tool redirects the browser to MiniVLE’s authorisation flow.
  5. MiniVLE returns a signed id_token to the tool launch endpoint.
  6. The tool verifies the token before creating its session.

Validate every launch

  • Signature and kid against MiniVLE JWKS.
  • iss, aud, authorised party where present, nonce, expiry, and issued-at time.
  • Deployment ID, message type, context, roles, and target-link URI.

State and nonce are mandatory

They bind a browser response to the launch your tool initiated and prevent replay and cross-site login attacks.

Scope and boundaries

Request the smallest scope your tool needs. The planned complete implementation will issue short-lived client-credentials tokens using private_key_jwt, validate audience, and bind tokens to registration, deployment, course, and approved scopes.

Planned service work

Standard AGS line items/results, Deep Linking requests/responses, and registration-scoped client credentials are planned. Do not depend on them yet.

{% elif section == 'testing' %}

Keep a repeatable route: one local MiniVLE, one local tool, a test course, and a learner account with no administrative privileges.

  1. Register the tool and add it to one test course.
  2. Launch as a learner and validate decoded claims in the tool.
  3. Launch as an instructor and confirm role handling.
  4. Call roster and score testing endpoints only with authorised development credentials.
  5. Review the course LTI page and platform audit log after each attempt.

Testing hosted LMSs

A hosted LMS cannot reach your machine’s localhost. Expose the local tool with an HTTPS tunnel, update registration URLs, then test against that LMS’s test environment.

Reset safely

Use a dedicated test course and tool registration. Delete only its placements, registrations, and test submissions in MiniVLE’s native UI; never reset shared production data.

{% else %}

Most integration failures are configuration mismatches. Start with the audit record, then compare each value sent and expected.

Unknown client ID or unrecognised issuer

Check the exact MiniVLE issuer and client ID for this environment. Localhost and a tunnel hostname are different issuers.

JWKS key ID or signature validation failed

Refresh MiniVLE’s JWKS, select the matching kid, and verify only against public keys.

State, nonce, or redirect mismatch

Expire state quickly, bind it to the browser session, and ensure the return URL exactly matches the registered redirect URI.

Deployment, placement, or service access failed

Confirm the placement is active, the learner is enrolled, and the requested scope is approved for that deployment.

Local launch differs from a hosted LMS

Use HTTPS, inspect SameSite cookie settings, and test through a tunnel because hosted services cannot call your localhost address.
